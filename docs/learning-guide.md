## Four tabs, one selected story

**Why NeMo Stack** explains the application’s purpose, the developer painpoints and each component’s contribution. **Integration Map** connects internal modules with labelled information flows. **Q&A** explains the boundaries and links back to the map. **Datasets → Data schema** preserves the dated audit comparison, with readable field labels grouped as names/identity, personal details, location, education/work, skills/interests, narratives and OCEAN.

Open **Datasets → Explore profiles** to read a bounded page from either installed original distribution. Choose HF public or NGC Extended, enter text and optional age, area and education constraints, then **Apply filters**. Source-wide option counts remain distinct from the matching result count. **Clear filters** restores that distribution. Select a profile to inspect its original fields, source revision, row hash and NGC trait JSON; the HF source has no names or OCEAN fields to invent. Paging and filtering make zero inference calls. Filters and the chosen subtab persist locally; raw rows are not saved in browser preferences or bundled into the guide. Missing data or a disconnected reader shows an explicit error with access to the schema reference.

The default is **Trace a Request → Find a photography class → Step 1 of 9**. Choose one scenario; its persona, harness and baseline model are preset context. Collapse setup to focus on the right-panel walkthrough. There are no independent configuration pickers to combine into a product matrix.

Select a block or module to inspect its responsibility and application connection. **Application code** opens the actual allowlisted repository-relative file/symbol and excerpt, with a direct GitHub committed-reference link where available. New unpublished files say publication pending. Recorded source hashes distinguish working-tree changes. **Scenario log** opens the selected fixed recording's matching files on GitHub, with verified in-app previews. Raw private-run links retain their existing local behavior; future live-log changes are deferred. Back, Next, Play, Reset and source/log inspection never start inference.

## Start with photography

The request is simple: a beginner photography class on Saturday, within S$50 before funding. The preset uses Fabric with Deep Agents and a fixed model through LiteLLM.

To inspect the actual recording, expand **Selected photography run** and retain its run identity across stages. Stage 4 shows the saved public UserSim request and actual advisor reply. The dated snapshot records a S$10 published fee and Saturday session for CC-001; material fees, current seats and personal funding eligibility remain unconfirmed. Choosing **Illustrative walkthrough** instead shows authored content with no execution claim.

Advance through nine slots: choose a persona, create a situation, build/connect, run, investigate, evaluate, optimize routing, safeguards and controlled deployment. Photography uses authored constraints in stage 2 and inspects its actual fixed LiteLLM route in stage 7. Relay provides native observability; application assertions inspect saved replies without evaluation inference. Designer, Switchyard, native Guardrails and Helix are omitted. Standalone OpenShell contains the persistent application/harness and course tools; UserSim and the budget gateway remain on the host. The nine slots do not require nine conversations or SDK calls at every stage.

At stage 5, choose a saved public turn, gateway call or native tool request. Highlighting follows that record's attributable boundary; it never invents a missing Relay-to-gateway span join. Stage 6 exposes each assertion's expected/actual value, reason and coverage. An exact catalogue URL is a valid source identifier even when the public reply omits internal course IDs. Stage 9 opens the loaded native YAML/revision, denial probes and confirmed cleanup.

To create fresh evidence, choose **Simulate a Session**, check prerequisites, select HF profile-only or Singapore NGC Extended, then **Choose a random test persona**. Inspect its identity/revision/hash and click **Start live photography simulation**. The advisor sees only the public message; the private original stays with UserSim. One condition may run at a time. Cancellation is explicit; changing tabs, inspecting code or closing the panel does not cancel it. Uncertain cleanup keeps a recovery guard instead of silently starting a second condition.

On **Why NeMo Stack**, each **Locate in the Map** button opens the corresponding step. Its accompanying external links open the HF/NGC dataset pages or current official library documentation. The contextual code inspector retains pinned API references alongside application excerpts, so newer documentation does not imply that the installed integration has been upgraded.

The [current verification](verification.md) identifies this implementation's actual checks and preserved failures. Historical photography/OpenShell evidence in the [v0.2 archive](history/v0.2/docs/verification.md) remains separate and does not establish current readiness.

## Try the two other situations

**Learn to play board games** uses Fabric/Hermes and a fixed model through LiteLLM over two authored public turns. The first request leads to an honest catalogue no-match. The second asks, “Is video-game design the same as playing board games?” The advisor should explain the distinction and preserve the no-match, without inventing a listing or treating a design course as an answer to the original goal. Stage 2 remains an authored situation and stage 7 remains fixed-route explanation; neither runs Designer nor Switchyard. Stage 8 introduces a separate native Guardrails probe rather than blocking this legitimate no-match request.

**Build skills for my dream job** is assigned Fabric/Deep Agents, Data Designer generation of hypothetical preferred-brand/salary columns, and dynamic Switchyard routing through LiteLLM. A UNIQLO or Decathlon ambition motivates learning retail sales, spreadsheet or inventory skills; the application is not a job site and has no verified employer-requirements feed. Its three authored public turns introduce the learning goal, voluntarily disclose a hypothetical salary band, then state an explicit training budget and study constraints.

The S$2,500–3,499 gross monthly salary band belongs to private simulator context until turn 2. A S$3,000 budget, weekend availability and preference for shorter options arrive in turn 3. The approximately six-month/S$20,000 programme is hypothetical. Do not treat it as a provider listing, infer affordability from salary or promise employment or earnings. The current wireframe illustrates these fields and routing responsibilities; it has not generated them through Designer or produced an actual Switchyard decision.

## Remaining scenario implementation

The shared foundation now supplies run/condition/episode/request identities, actual tool results, native provenance and role-labelled usage for photography. New scenarios must use those same contracts with their own verified configurations, recordings and missing-evidence states. Playback and inspection must continue to make zero inference calls.

Each scenario retains all nine stage slots while using only the components its lesson needs. Photography is one turn and board games is two, both with authored situations and fixed routes. Actual Designer generation, native routing and Helix operations are acceptance obligations of the three-turn retail-learning story. Board games introduces native Guardrails through a separate probe; the ordinary no-match stays allowed. Photography uses application restrictions without native Guardrails. Both simpler presets use application assertions without Helix. Configure its route before execution and inspect the same conversation’s decisions later; do not rerun solely to fill a routing stage.

Controlled harness comparisons are separate fixed-model experiments. Fixed-versus-routed comparisons keep the harness, source records, public inputs and frozen catalogue fixed in an explicitly named condition. Application assertions are distinct from native Helix scoring. Scenario 3 introduces Helix Evals plus explicit Platform evaluation jobs and registered-agent, deployment and session operations. Effective OpenShell policy plus actual allow/deny and cleanup receipts establish enforcement; policy examples alone do not. All planned live runs contain the application, its one persistent selected harness and course tools inside OpenShell: standalone for scenarios 1/2 and Helix-managed for scenario 3. Reusable packages receive public context at runtime; no persona-specific image or private salary is required.
