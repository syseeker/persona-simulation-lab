# v0.2 Integration Learning Plan

## Goal and decision rule

The [North Star](docs/project-goals.md) is the source of truth: help a developer build, demonstrate and debug a citizen-focused application through a coherent UI journey, with each NeMo responsibility linked to actual code/configuration/evidence. Singapore courses and activities are the example, not the boundary of the reusable architecture.

The [v0.1 plan and verification](docs/history/v0.1/INDEX.md) remain historical. Implementation and offline evidence do not imply current live readiness.

## Delivery slices

1. **One story and honest outcomes.** Named photography, baking and board-game stories; one selected episode throughout inspection; new conditions only for a stated comparison. Preserve failed final answers and incomplete traces rather than returning runtime error strings as advisor success.
2. **Visible application flow.** Source-profile/scenario separation, UserSim activation evidence, MCP requests/results, native Relay relationships, Fabric runtime/harness identity, proxy routing, artifacts and local source references.
3. **Persona and Data Designer workbench.** Full local HF corpus, separate Singapore NGC Extended readiness, inspect/filter/sample/lock/replay. Generate source-seeded scenarios, six supported custom-field types and new synthetic rows. Preserve hashes, parentage, typed validation and hypothetical labels.
4. **Harness and model infrastructure.** Retain direct/Relay Deep Agents; add maintained Fabric/Hermes integration in its compatible environment. Keep harness comparisons on a fixed model; make Switchyard routing through LiteLLM an explicit alternative with native decision evidence.
5. **Evaluation and deployment.** Explain per-turn local Helix assertions and unsupported/not-applicable evidence. Provide explicit local/remote Platform connection and registration/deployment/session paths, and the OpenShell agent/tool boundary. External-service availability must be established by actual probes and execution.
6. **Durable learning material.** Update README, walkthrough, architecture/diagrams, interfaces, persona rules, compatibility and coaching together. Preserve the v0.1 archive and record v0.2 verification separately.

## Acceptance

A developer can demonstrate a distinct story entirely in the UI, reopen the same saved run without inference, explain the component transitions, locate integration code and inspect actual native artifacts. Random selection changes source IDs; locking reuses exact source records. Designer generation creates inspectable hypothetical values and new identities, and saved generated data can become explicit simulation input.

A no-match request remains a no-match across supported harnesses. Provider errors, empty answers, turn-limit stops and pseudo-tool markup cannot pass as valid answers. Helix exposes criterion-level reasons and unavailable evidence before an aggregate score. Cancellation retains partial output and measured/unknown usage.

Native runtime IDs, Relay spans, routing decisions and sandbox enforcement must come from the component that owns them. A configured endpoint, generated YAML or local fixture cannot be called live verification. Read [verification](docs/verification.md) for the observed state and remaining environmental requirements.

## Defaults and boundaries

One story, one profile, one strategy, fixed-model comparison, fresh target state per condition; up to three public conversation turns and 120 admitted calls per workload. Data Designer previews default to five rows. Original rows and generated hypotheses are never merged destructively.

Preserve SvelteKit plus the persistent Python worker and supported isolated environments. The advisor keeps the read-only course MCP surface; developer-control services do not become agent tools. Dataset download/access, live generation, Platform mutations and sandbox execution remain explicit operations. Booking, payment, Singpass and unrestricted catalogue crawling remain outside this sample.
